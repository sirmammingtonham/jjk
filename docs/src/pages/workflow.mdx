# The stacked-PR workflow

This is the **manual** flow: you create branches and commit to them yourself, one PR per branch. If
you'd rather work on a single branch and let an LLM split it into a stack, see
[Domain Expansion](/domain-expansion) — it's the automatic counterpart and reuses everything below
(submit, review, merge, sync).

## Mental model

- A **branch** is one PR: a [jj bookmark](https://jj-vcs.github.io/jj/latest/bookmarks/) sitting at
  the tip of a contiguous range of commits. Multiple commits per branch is normal.
- Your working copy is always an empty change on top of the current branch tip. `jjk commit`
  finalizes your edits into a real commit and advances the branch.
- The stack graph is **derived from jj at runtime**, so there's nothing to keep in sync and nothing
  to corrupt. The only thing `jjk` stores is the branch to PR-number mapping.
- You can keep using plain git where it's handy. A `git checkout <branch>` is followed by jjk (it
  reconciles position to git's `HEAD`), and `git add` drives what `jjk commit` commits — jj still
  handles the rebasing and conflict resolution underneath.

## 1. Build the stack

```bash
jjk branch create feat-a
# ...edit, jjk commit...
jjk branch create feat-b      # stacked on feat-a
# ...edit, jjk commit...
```

Editing a lower branch **auto-restacks everything above it**. jj rebases the descendants when an
ancestor changes, and `jjk` just records the bookmarks that moved. `jjk restack` exists for parity
but is usually a no-op.

```bash
jjk ls    # the stack, top to bottom
jjk ll    # the stack, with each branch's commits
```

```
    ┏━■ feat-c ◀
    ┃   9a6c68f9b7 polish ui (2 minutes ago)
  ┏━┻□ feat-b
  ┃    cb82c87f73 wire up handler (5 minutes ago)
┏━┻□ feat-a
┃    0041183abc add feature flag (8 minutes ago)
main
```

## 2. Submit

```bash
jjk submit
```

This pushes each tracked branch (force-with-lease), opens a PR per branch based on its downstack
branch (or trunk for the bottom), and adds a **stack-navigation comment** to each PR listing every
PR in the stack and marking the current one with `◀`:

```
🥞 This change is part of the following stack · PR 3/3

- #19
    - #20
        - #21 ◀
```

`submit` is **idempotent**. Re-running it after edits updates the existing PRs and comments in
place, and never creates duplicates.

## 3. Iterate during review

Address feedback on any branch, including mid-stack:

```bash
jjk down                         # go to the branch under review
# ...make changes...
jjk commit -m "address review"   # upstack auto-restacks
jjk submit                       # update all affected PRs and bases
```

To amend the tip of a branch instead of adding a commit:

```bash
jjk commit --amend -m "reworded"
```

Started editing on the wrong branch? Switching carries uncommitted changes along (like `git
checkout` with a dirty tree), so you can move work to where it belongs and commit there:

```bash
# ...realize these edits belong one branch down...
jjk down                         # uncommitted changes come with you
jjk commit -m "fix on the lower branch"
```

## 4. Merge and sync

Merge the **bottom** PR on GitHub. Squash and merge-commit are both handled. Then:

```bash
jjk sync
```

`sync` does the following:

1. Fetches, so your local trunk fast-forwards to include the merge.
2. Asks GitHub which PRs are merged.
3. Rebases the **whole remaining stack** onto the new trunk.
4. Reconciles the merged branch. It abandons the now-empty change (squash) or drops the bookmark
   (merge-commit) so the next branch reconnects directly to trunk.
5. Force-pushes the survivors and **retargets their PR bases** (the next branch's base becomes
   `main`).

The result is clean upstack diffs, with no duplicated or garbled content, regardless of how the
bottom PR landed.

To reconcile your local state without touching the remote, use `jjk sync -n` (`--no-push`): it
fetches, drops merged branches, and rebases the stack onto trunk, but doesn't force-push or retarget
PRs. Handy after a teammate merges something, when you're not yet ready to update your own PRs.

`jjk pull` is the even lighter cousin. It fetches and rebases the stack onto trunk, but does no
merged-PR detection and no push.

## Conflicts

jj stores conflicts inside commits, so a `sync` (or any rebase) **completes and reports** the
conflict instead of halting partway like `git rebase`. When `jjk` prints
`CONFLICT: N change(s) need resolution`, it walks you through them git-style:

```bash
jjk resolve              # jumps to the first conflict and lists exactly which files to fix
# ...edit the marked files (only those — the rest of the change is already correct)...
jjk resolve --continue   # records the fix, then moves to the next conflict, or finishes
```

Run `jjk resolve --continue` once per conflict. When the last one is resolved it puts you **back on
the branch you started on** and re-runs the `sync` for you, so the now-fixed branches get pushed.
`jjk status` reminds you where you are while a resolution is in progress.

Two extra options:

```bash
jjk resolve --interactive   # resolve with your configured merge tool, one file at a time
jjk resolve --abort         # give up and rewind to the state from before the sync
```

Conflicts are shown with standard git-style markers (`<<<<<<<` / `=======` / `>>>>>>>`). New repos
get this automatically; on a repo you set up before this was added, enable it once with:

```bash
jj config set --repo ui.conflict-marker-style git
```

## Working on several branches at once

Each [jj workspace](https://jj-vcs.github.io/jj/latest/working-copy/#workspaces) is its own working
directory sharing the same repo. This is handy for running multiple agents in parallel, one per
branch:

```bash
jjk worktree add ../agent-b --branch feat-b
jjk worktree list
```

The current branch is tracked per-workspace. If a `sync` or `commit` in one workspace rewrites
history, other workspaces are **automatically recovered** the next time you run a `jjk` command
there.
